### 本轮修复的明确取舍

1. ASR 收尾/实际插入窗口中的新按键不排队，用户需等当前段交付后再开始；下一版可以引入明确队列和 UI 忙碌提示。
2. 损坏历史采取保守保数据策略，修复索引前暂停新历史保存；应继续补一个“历史无法读取、保存暂停”的界面状态和修复入口。
3. 系统流在成功注册前的少量样本被丢弃，优先避免旧流混入；启动首音节和快速 stop/start 需实际采集验证。
4. 自动重连的 30 秒是稳定窗口策略，不代表云端识别结果质量保证。用户显式重新开始可立即重置预算。

## 仍需优先开发的设计问题

### 1. P1：统一“保文字”终结流程

**证据**：`DictationController.startEngine.onError` 在错误停留后清掉 session/overlay，没有交付 `bestTranscript`。已有流式识别结果时断网，文字仍可能丢。`hotSwapEngine` 的 batch stop completion 把迟到片段前插，按返回顺序而非录音顺序组装；结束录音也没有等待所有退休 batch。

**改法**：把一次录音拆成有序 segment（序号、引擎、时间、final/interim、完成状态），建立一个统一 `finish(reason:)`，只有 explicit cancel 丢弃。网络错误/超时交付当前最优文本；finalize 对待完成 segment 有总期限，按序拼接并防重复交付。短期产品方案是 batch 切换只对下一次录音生效，不再热切换。

**验收**：A→B→C 录音而回包 B→A→C 时仍输出 A B C；旧 batch 失败不清掉新段；断网保留已识别字；最终 stop、取消、超时并发只交付一次。

### 2. P1：事后纠正不应盲目全局撤销

**证据**：`System/TextInjector.swift` 的 `replaceLastInjection` 使用全局 Cmd-Z，再粘贴纠正内容。用户粘贴后又打字、换输入框或切应用时，撤销目标可能已不是那次语音输入。

**改法**：优先使用“插入前确认”。保留“插入后纠正”时，记录 AX 目标元素、原始范围和插入文本，只有能验证目标与内容未变化时才替换；无法验证时提供复制纠正结果，而非盲目 Cmd-Z。需要明确用户手动编辑优先级。

**验收**：粘贴后键入其他文字/换窗口/换字段，纠正不撤销新编辑，也不写到错误应用。

### 3. P1/P2：历史、纠正学习与隐私删除应共享清晰的数据规则

**证据**：History 的“清空”文案称删除所有保存转录，但 `Core/CorrectionStore.swift` 永久追加 raw/injected/corrected 到 `corrections.jsonl`；`HistoryStore.clearAll` 不清它，关闭 history 也没有关闭这条学习存储路径。API key 则写在 AppSettings 的 UserDefaults 和预设 JSON。

**改法**：增加独立“保存纠正用于学习”开关和期限；区分“清空历史列表”与“删除全部个人语音数据”，后一操作覆盖纠正、自动学习词汇和相应统计。密钥按 provider/preset ID 放 Keychain，必须成功写入并读回后才移除旧值，不能直接切换读取导致原配置失效。

**验收**：关闭学习不落纠正全文；全量删除后重启亦无残留；旧密钥迁移失败时原配置仍可用；测试 ad-hoc 签名更新下 Keychain 授权行为。

### 4. P2：字幕错误态必须能完整恢复

**证据**：`ListenController.enterTerminalError` 停采集但保留 `state.active=true`；provider/target 变化只执行 `restartSessionCarryingText → startSession`，没有恢复 capture，可能显示已连接却没有音频。

**改法**：用 stopped/starting/running/reconnecting/failed 状态统一管理 session 和 capture，增加明确的重新连接操作；从 failed 恢复时恢复两者，普通自动重连只替换网络 session，避免双录音流。

### 5. P2：历史写入需要提交语义和可见错误

**证据**：`HistoryStore.writeRecordsToDisk` 失败只记录日志，调用方仍发布“新列表”；删除/保留策略先删 WAV 再写索引。磁盘满时可能界面像成功而重启后消失，或索引还在而音频已被删。

**改法**：写盘返回 Result，只发布已提交状态；先提交新索引再删除不再引用的音频，孤儿清扫作善后。损坏、满盘、无权限分别显示可恢复错误。录音存储和容量应有独立策略，避免任何一次小编辑重写全部历史。

### 6. P2：批量识别的等待与时长上限没有向用户说清

**证据**：`SonioxAsyncSession` 已拿到转录后先 await 两个 DELETE cleanup，再交付文本；清理失败会拖延已完成结果。`AudioCapture` 的 WAV 保留有十分钟上限，而 batch 使用同一 WAV，界面却仍可持续录音。

**改法**：先完成文字交付，云端清理独立受控重试；用文件流式记录或分片上传，并明确最大录音时长。取消后的清理任务需要独立生命周期；当前取消传播是否阻断 DELETE 应用 URLProtocol fixture 验证，不当作已经在线复现的结论。

### 7. P2/P3：最终纠正版本和统计不一致

**证据**：`HistoryRecord.bestTranscript` 和 `HistoryView` 只优先 refined/raw，已保存的 `correctedTranscript` 没有在详情作为最终版本展示。`CorrectionStore` 的周计数缓存只有追加后失效，应用长期开着会把已过七天的记录继续计入。

**改法**：历史明确展示 Raw/Refined/Corrected，列表、搜索和默认复制使用实际最终版本；区分 nil 与用户故意改成空串。时间统计注入时钟、缓存带期限，添加跨周边界测试。

## 建议开发顺序

1. 先验收本轮修复，随后做 session/segment 状态机和可注入的 controller 测试夹具，解决断网保字、batch 乱序和重复交付。
2. 再做安全的输入目标定位与插入前确认流程，避免全局撤销损伤用户编辑。
3. 再统一个人数据删除/保留、Keychain 迁移与历史事务，补清晰的失败/恢复 UI。
4. 最后补字幕恢复、最终纠正展示、协议 fixture 和文档同步；风格统一、控件布局等应在这些正确性问题之后。

## 人工验收清单（未在本轮执行）

- 停止后在 ASR 收尾、润色和插入倒计时分别按 Cancel/Esc：不得迟到插入，界面不得被旧任务重新打开。
- 听写中连续换 provider/backend：旧引擎报错不得清新引擎；batch 片段顺序问题仍按上述后续项处理。
- 系统音频权限弹窗未结束时关闭字幕，再切麦克风：旧权限请求完成不得停止或污染新采集。
- 服务持续 429/5xx：1/2/4 秒重试后显示错误并停止采集，而非永远循环。
- 临时测试账户/目录中损坏历史文件：WAV 与原文件保留；不要直接损坏个人真实历史做验收。
